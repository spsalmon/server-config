# CLAUDE.md

NixOS flake config for Sacha's home server: a **media server** (nixarr: Jellyfin + *Arrs +
Transmission) that doubles as a **personal file-sync service** (Syncthing) and a **Tailscale
exit node**.

The whole thing runs on **an old laptop with a GeForce GT 650M**, lid closed. That single fact
drives most of the non-obvious decisions in this repo — read "The machine" and "Transcoding
reality" before proposing anything that costs CPU, disk, or a kernel rebuild.

## Deployment model — read this first

This working copy lives on a **WSL dev machine**, not on the server. There is no `nix` binary
and no `/etc/nixos` here, so **nothing in this repo can be built, evaluated, or tested from
this checkout**. Don't suggest `nix flake check`, `nixos-rebuild build`, or `nix repl` locally —
they will fail.

The workflow is:

1. Edit here, commit, push to `git@github.com:spsalmon/server-config.git` (branch `main`).
2. SSH into the server (over Tailscale), `git pull`, then:
   ```sh
   sudo nixos-rebuild switch --flake .#default
   ```

Consequences for how to work in this repo:

- Correctness must come from careful reading of Nix option names, not from a local build.
  When unsure whether an option exists or was renamed, say so explicitly rather than guessing —
  a bad option name means a failed rebuild, and on this hardware a failed rebuild is an
  expensive round trip.
- **Rebuilds are slow.** Ivy Bridge-era mobile CPU, spinning laptop disk. Anything that forces
  a local compile instead of a binary-cache hit (a kernel change, an unfree/legacy driver, an
  override) can turn a two-minute switch into an hour. Prefer changes that stay on the cached
  path.
- Prefer small, self-contained commits: each push is a manual rebuild on the other side.
- `nixpkgs` tracks **nixos-unstable** and `nixarr` tracks its **`dev` branch**, so option
  renames are a recurring source of breakage (see "History of pain").

## Layout

```
flake.nix                              inputs + the single `default` nixosConfiguration
flake.lock                             pinned inputs (nixpkgs unstable, nixarr dev, ...)
hosts/default/configuration.nix        host-level config; imports every module
hosts/default/hardware-configuration.nix   generated by nixos-generate-config — do not edit
modules/nixos/nixarr.nix               media stack (Jellyfin, *Arrs, Transmission, DDNS)
modules/nixos/syncthing.nix            personal file sync
modules/nixos/tailscale.nix            tailnet + exit node + firewall policy
modules/nixos/nvidia.nix               GT 650M driver config — currently inert, see below
modules/nixos/turn_screen_off.nix      logind lid-switch handling (name is now a misnomer)
```

One host (`default`, hostname `nixos`). No home-manager, no overlays, no secrets module.
Modules are plain `{ config, pkgs, ... }: { ... }` files imported by
`hosts/default/configuration.nix`; **a new module must be added to that `imports` list** or it
silently does nothing.

## The machine

An **old laptop** — a GT 650M puts it in the 2012–2013 Ivy Bridge generation, so expect a
dual/quad-core mobile i5/i7 with an Intel HD 4000 iGPU alongside the NVIDIA chip (classic
Optimus). Exact CPU and RAM aren't recorded in this repo; check on the box if it matters.

- **GPU: NVIDIA GeForce GT 650M** — Kepler, GK107. See "NVIDIA" below; the constraints are
  sharper than they look.
- Intel CPU (`kvm-intel` in `hardware-configuration.nix`).
- **Storage: a 500 GB WD Scorpio laptop drive** (`ata-WDC_WD5000BPKT-...`), i.e. a small,
  slow, spinning 2.5" disk. `/` lives here along with the Nix store.
  - GRUB targets it **by-id** on purpose; `/dev/sda` broke booting once (`7d1560e`).
  - Disk pressure is a real failure mode. `sudo nix-collect-garbage -d` after a few flake
    updates, and keep an eye on `df -h /` — a full root disk breaks rebuilds *and* the
    services at the same time.
- **`/mnt/media` is a separate ext4 disk** (UUID `9bda785c-…`) — all media and nixarr state.
  Keep media off `/`.
- A swap partition is configured; on a machine this old, swapping to the spinning disk is
  effectively a hang. Avoid memory-hungry additions.
- Lid closed permanently — `turn_screen_off.nix` tells logind to ignore the lid switch so it
  keeps serving. This also means **it runs hot with poor airflow**: sustained CPU transcoding
  will thermal-throttle, which is another reason direct play matters (below).
- `system.stateVersion = "23.11"` — leave it alone.
- Locale `en_US.UTF-8`, timezone `Europe/Zurich`, **French (`fr`) keymap** in X11 and console.

## NVIDIA (`modules/nixos/nvidia.nix`) — read before touching

Two things are true at once here, and both matter.

**1. `legacy_470` is correct and mandatory — never "upgrade" it.**
The GT 650M is Kepler. NVIDIA dropped Kepler support after the 470 branch, so
`nvidiaPackages.legacy_470` is the *last* driver that works with this card. It is EOL upstream
and will never gain features. A well-meaning bump to `stable`, `production`, or `latest` will
leave the GPU with no usable driver. The commit history already shows this lesson:
`stable` → `legacy_470` in `befd94e`, "switched drivers to the correct version". Do not undo it.

**2. The module is currently inert — the GPU is almost certainly not in use at all.**
`services.xserver.videoDrivers = ["nvidia"];` is **commented out**, and has been since the very
first NVIDIA commit (`f9f2ebf`, May 2024, "adding nvidia support for transcoding"). In NixOS the
whole `hardware.nvidia.*` block is gated on `"nvidia"` appearing in `videoDrivers` — without it
the kernel module isn't loaded and no `/dev/nvidia*` nodes exist. So despite the module's
intent, everything in it is dead config, and Jellyfin has been transcoding **on the CPU** this
whole time. Verify on the box before acting on this:

```sh
lsmod | grep -i nvidia
ls /dev/nvidia*
nvidia-smi
```

That dormancy is probably also why the system still builds — see the kernel risk below.

**If the user wants to actually enable the GPU**, treat it as a project, not a one-liner, and
warn them up front:

- Uncommenting `videoDrivers` starts building the 470 kernel module against
  **nixos-unstable's kernel**, which moves fast. The 470 branch stopped building against recent
  kernels; this will likely need `boot.kernelPackages` pinned to an older LTS
  (`pkgs.linuxPackages_6_6` or similar). That pin is currently absent — the kernel is whatever
  unstable ships.
- A pinned older kernel plus an unfree legacy driver means **compiling on this laptop**. Budget
  real time.
- Even then, see the next section for whether it's worth it.

`hardware.graphics.enable = true` (renamed from `hardware.opengl` in `e11fff5`) is the one line
in this module that does something today. `open = false` is required — the open kernel modules
are Turing+ only. Both `powerManagement` options are `false`.

## Transcoding reality

The goal is **as little transcoding as possible**. Set expectations honestly here rather than
promising hardware acceleration this box can't do.

### The hardware floor

**This machine has zero hardware HEVC/H.265 decode.** Neither GPU can do it:

- **GT 650M (Kepler GK107):** first-generation NVENC and a VP5 decoder — H.264, MPEG-2, VC-1
  only. NVIDIA HEVC decode arrived with Maxwell (GM206). No VP9 either.
- **Intel HD 4000 (Gen7 QSV):** H.264/MPEG-2/VC-1 decode, H.264 encode. Intel fixed-function
  HEVC decode didn't arrive until Skylake (Gen9).

So any HEVC file Jellyfin is forced to transcode gets **decoded on the CPU**, and decode is the
expensive half. Offloading the encode shifts the ceiling; it does not remove it.

### But HEVC in the library ≠ a transcode

Increasingly, some shows and films are **only available as H.265** — that is a fact of
acquisition now and cannot be avoided by preference alone. It is not automatically a problem:
Jellyfin only transcodes when the *client* can't play the stream. Most clients from ~2015 on
decode HEVC natively (Apple TV 4+, iOS/Android, Shield, Fire TV, modern smart TVs), and for
those this laptop is just a file server.

What actually forces a transcode, in rough order of how often it bites:

1. **Image-based subtitles** — PGS/VOBSUB, and styled ASS/SSA, get burned in, forcing a full
   video transcode even when the codec was fine. **The most common surprise transcode.** Bazarr
   is already enabled; prefer **SRT** (text) subtitles, which are sent to the client to render.
2. **A client-side quality cap** — anything other than maximum/direct-play bitrate requests a
   transcode regardless of codec. Per-device setting, easy to miss.
3. **HDR / 10-bit to an SDR client** — tone mapping is brutal and this box cannot do it at a
   watchable framerate. Prefer SDR.
4. **Browsers** — Safari plays HEVC; Firefox generally won't; Chrome/Edge need the platform
   extension. Browser playback is the most likely silent transcoder.
5. **Container/audio only** — MKV remux and audio-only transcodes are cheap. Not the problem.

Before optimizing anything, check Jellyfin's dashboard for *why* a given stream is transcoding —
it names the reason, and the fix is usually (1) or (2), not the codec.

**Known client mix (Aug 2026): a TV/streaming box, and a browser on a computer.** The TV box
almost certainly direct-plays HEVC; the browser is the problem case, and HEVC + a browser +
image-based subtitles is the worst combination this hardware can be handed. Prioritize browser
playback and subtitle format over anything server-side.

### When a transcode really is forced

Rough shape on an Ivy Bridge mobile chip: 1080p 8-bit HEVC → H.264 is borderline, maybe fine for
a single stream with nothing else running. 1080p 10-bit is worse. **4K HEVC is not happening at
any settings.** It also competes with the *Arrs and Transmission for the same weak CPU and the
same slow spinning disk, and the closed lid means it throttles.

### Levers, and where they live

Most mitigations are **not in this repo** — they're Jellyfin/Bazarr/*Arr settings in their own
UIs and state dirs. Don't imply a Nix change can fix a client-side transcode trigger.

The one genuine in-repo lever: `hardware.graphics.enable = true` is set, but there are **no
VAAPI drivers in `extraPackages`**, so the iGPU can't be used for encode today. Adding
`intel-vaapi-driver` (**i965** — Gen7; *not* `intel-media-driver`, which is Gen8+) is a small,
low-risk change that lets Jellyfin offload the H.264 encode side. Verify the package name is
still current in unstable first. HEVC decode stays on the CPU regardless.

**Decision (Aug 2026): the user declined this for now**, in favour of fixing transcodes at the
client and acquisition end. Don't re-propose it unprompted — revisit only if forced transcodes
persist after the client-side fixes.

NVENC on the GT 650M is **not** the better path, despite the card being there: beyond needing
`videoDrivers` enabled (see NVIDIA above), current ffmpeg in nixpkgs is built against
`nv-codec-headers` requiring a far newer driver than 470, so it would mean pinning older
headers/ffmpeg — a large yak shave for an H.264-only encoder the iGPU already provides.

On acquisition (Radarr/Sonarr custom formats, TRaSH Guides): prefer H.264 where a release
exists; where only HEVC exists, bias toward **1080p 8-bit SDR** over 10-bit/HDR/4K. `recyclarr`
can manage these declaratively and is likely packaged in nixpkgs — verify before promising it.

## Networking & security model

**Tailscale is the security boundary.** `modules/nixos/tailscale.nix` sets
`trustedInterfaces = [ "tailscale0" ]`, so anything listening is fully reachable from the
tailnet regardless of `allowedTCPPorts`. Services are therefore not individually firewalled for
tailnet access — only for LAN/WAN.

- `useRoutingFeatures = "server"` + `--advertise-exit-node`: the box is an **exit node**. The
  route still has to be approved once in the Tailscale admin console; not expressible here.
  (Exit-node throughput is bounded by this laptop's NIC and CPU — don't expect gigabit.)
- `networking.nftables.enable = true`, and `tailscaled` is forced to
  `TS_DEBUG_FIREWALL_MODE=nftables` to avoid iptables-compat breakage on an nftables-only
  system. If you touch the firewall, keep that env var.
- `systemd.network.wait-online` is disabled (both stages) for faster boots.

LAN/WAN-open ports, from `hosts/default/configuration.nix`:

| Port | What |
|------|------|
| 80, 443 | nginx / ACME for the Jellyfin HTTPS exposure |
| 8096, 8920 | Jellyfin HTTP / HTTPS |

Plus Syncthing's `openDefaultPorts` (22000/tcp, 22000/udp, 21027/udp) and Tailscale's UDP port.

**SSH is deliberately not in that list.** Commit `849aba9` removed port 22, so sshd is reachable
**only over Tailscale**. `PasswordAuthentication` is currently `true` — acceptable only because
of that. If you ever re-open 22 to the LAN/WAN, turn password auth back off in the same change.

Tailnet-only by design (not in the port list): every admin UI — Sonarr (8989),
Radarr (7878), Transmission RPC/web (9091), Prowlarr (9696), Lidarr (8686),
Bazarr (6767), Syncthing GUI (8384). Sonarr, Radarr and Transmission were open to
the LAN until they were removed from `allowedTCPPorts`; tailnet access was
unaffected because `trustedInterfaces` already covers it. The *Arrs reach each
other and Transmission over loopback, so closing these breaks nothing internally —
but a LAN device *not* on the tailnet can no longer reach them.

## nixarr (`modules/nixos/nixarr.nix`)

Input: `github:rasmus-kirk/nixarr/dev`, with `nixpkgs` following ours.

- `mediaDir = "/mnt/media"`, `stateDir = "/mnt/media/.state/nixarr"`. **Never point these at
  `/home/...`** — nixarr's permission model breaks; its own comment says so.
- Enabled: `jellyfin`, `transmission`, `bazarr`, `lidarr`, `prowlarr`, `radarr`, `sonarr`.
  `readarr` was removed (`0fd175b`) — don't re-add it unprompted. Every additional *Arr is
  another always-on service competing for a weak CPU and one slow disk; think twice before
  suggesting more.
- `transmission.vpn.enable = false`. The commented `peerPort` only matters if a VPN with a
  forwarded port is enabled. nixarr can route the *Arrs through a VPN too, but its docs warn
  that causes rate-limiting — leave that off.
- `ddns.njalla` reads `keysFile = "/data/.secret/njalla/keys-file.json"`. That file lives **only
  on the server**, outside this repo and outside `/mnt/media`. Not in git, and must never be
  committed.
- `jellyfin.expose.https` builds an nginx reverse proxy + ACME cert for
  `jellyfin.marenglen.org` (`acmeMail = "mail@marenglen.org"`).

### Known broken: Jellyfin over the domain returns 502

`https://jellyfin.marenglen.org` used to work and now gives **502 Bad Gateway**. The user wants
this fixed. Nothing in the repo has obviously regressed, so it's most likely runtime state on
the server. Diagnose there, roughly in this order:

```sh
systemctl status jellyfin nginx
journalctl -u nginx -e            # 502 = nginx reached, upstream didn't answer
journalctl -u jellyfin -e
ss -tlnp | grep 8096              # is Jellyfin listening, and on what address?
systemctl status acme-jellyfin.marenglen.org.service
dig +short jellyfin.marenglen.org # does Njalla DDNS still point at the current WAN IP?
df -h /                           # cheap to check, and a full disk breaks things this way
```

Plausible causes, cheapest first: Jellyfin unit failed or bound to the wrong address after a
nixarr `dev` update; disk full; the DDNS record drifted; an ACME renewal failure; or nixarr
renaming the `expose.https` options underneath us. Check the current nixarr `dev` module source
before assuming the options in this file are still valid.

## Syncthing (`modules/nixos/syncthing.nix`)

Runs as user `sacha`, `dataDir = /home/sacha/Sync`, `configDir = /home/sacha/.config/syncthing`.
GUI on `0.0.0.0:8384` with `insecureAdminAccess = true` — only safe because 8384 isn't open
outside the tailnet. **Do not open 8384 in `allowedTCPPorts` without adding GUI auth.**

Note `/home/sacha/Sync` is on the **small root disk**, not on `/mnt/media`. Sync volume is
therefore bounded by whatever's left of 500 GB after the OS and Nix store. If the user wants to
sync something large, moving `dataDir` onto the media disk is the right call.

Gotcha worth remembering (`9ba0876`): setting `settings.gui.address` alone was not enough,
because Syncthing's on-disk `config.xml` wins. The fix was to *also* set the top-level
`guiAddress`, which passes `--gui-address` on the command line and overrides stored config. The
same class of problem applies to other `settings.*` values Syncthing persists itself —
declarative `settings` can lose to existing state.

Folders and peer devices are **not declared here**; they're set through the GUI and live in the
state directory. Making them reproducible means adding `settings.devices` / `settings.folders` —
a real change in approach, worth asking about first.

## Conventions

- Two-space indent, one concern per module file, comments kept from the upstream templates.
- Keep `hardware-configuration.nix` untouched; regenerate on the server if hardware changes.
- Commit messages are short and informal (`"fixing syncthing"`, `"updated flake"`). Match that.
- `nix flake update` is committed as a standalone `"updated flake"` commit — keep it separate
  from config changes so a bad bump is easy to revert. On this hardware a bump that lands a new
  kernel or a cache miss is a long rebuild, so don't update the flake casually as part of an
  unrelated task.

## History of pain (don't relearn these)

- **Driver version:** `nvidiaPackages.stable` was tried first and was wrong for Kepler;
  `befd94e` switched to `legacy_470`. Never go the other way.
- **Option renames from tracking unstable:** `services.openssh.passwordAuthentication` →
  `services.openssh.settings.PasswordAuthentication` (`61936f5`); `hardware.opengl` →
  `hardware.graphics` (`e11fff5`); logind lid settings moved under
  `services.logind.settings.Login` (`e11fff5`).
- **Bootloader:** GRUB on `/dev/sda` broke; fixed by using the stable by-id path (`7d1560e`).
- **Firewall:** it was disabled entirely at one point to make Jellyfin reachable (`fb91186`),
  then re-enabled with an explicit port list. Don't reach for `firewall.enable = false` again.
- `turn_screen_off.nix` originally ran a systemd unit calling `xset` to blank the screen; that
  approach was dropped and the file now only handles the lid switch. `xorg.xset` is still in
  `environment.systemPackages` as a leftover.
